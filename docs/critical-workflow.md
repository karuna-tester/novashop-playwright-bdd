# Critical Workflow: Nova Shop Purchase

## End-to-end flow

1. Open the shop and sign in using a locally configured standard-user account.
2. Search, filter by category or availability, and sort the catalogue as needed.
3. Open an in-stock product, inspect its detail content, choose an offered variant, and set a valid quantity.
4. Add one or more products to the cart. Change quantities or remove items as required.
5. Apply an advertised coupon and inspect its status, discount, tax, and total.
6. Continue to checkout. Enter the required contact and shipping fields, choose standard or express delivery, choose card or cash on delivery, and accept the terms.
7. Place the order and capture the generated order number, item count, delivery, payment method, and paid total from the confirmation.
8. Open My orders and verify the matching order and initial Processing status.
9. Optional alternate manager flow: sign in as the manager in the same browser storage, ship the order, and mark it delivered. The customer order history can then verify the updated status and available return behavior.

## Entry criteria

- The configured shop URL is reachable.
- The application displays the login form and its published practice accounts.
- The `.env` file contains the appropriate role account identifiers and practice password; it is not checked in.
- The test uses its own browser context. The app stores orders in browser localStorage rather than in a shared test database.
- For checkout, use synthetic contact details and only the app's published practice-card behavior; never use real personal or payment data.

## Test data

- Standard and manager identities: `SHOP_STANDARD_USER` and `SHOP_ADMIN_USER` from the local environment.
- Login secret: `SHOP_PASSWORD` from the local environment.
- Coupons: `SAVE10` and `FLAT20`, both shown by the cart.
- Invalid coupon: a non-advertised value such as `NOTREAL`.
- Product names, prices, availability, categories, and option lists are read from the rendered application at run time wherever a test needs them.
- Checkout uses reserved `.test` email data, a clearly fictitious address, and the site's documented synthetic test card.

## Expected outcomes

- Valid credentials enter the catalogue; rejected credentials remain on the sign-in flow with an error.
- Search, filter, and sort results reflect the selected criteria.
- Product and cart quantities obey the displayed bounds; unavailable products cannot be added.
- Coupon success/failure is visible and only a successful coupon changes the summary.
- Subtotal, discount, delivery, 8% tax, and total reconcile, including at checkout.
- Required or malformed checkout inputs report field-level validation and do not create an order.
- A successful order creates a dynamic order number, clears the cart, and appears in customer history with an initial status.
- Manager actions advance eligible orders through the supported statuses.

## Alternate and negative paths

- Empty/invalid credentials and a locked account.
- Slow-login account to exercise auto-waiting instead of fixed delays.
- No-result search, sold-out product, invalid coupon, and quantity limits.
- Missing checkout fields, invalid email/phone/ZIP/card/expiry/CVV, unchecked terms, and declined practice card.
- Express delivery and cash on delivery as alternate checkout paths.
- Customer cancellation and manager ship/deliver actions where the current status allows them.

## State and isolation

Each test starts from a fresh browser context backed only by the authenticated state generated by the setup project. The application stores order data in browser localStorage, so tests create and verify their own orders in one test context and do not assume order data is shared across browsers, tests, or CI jobs.
